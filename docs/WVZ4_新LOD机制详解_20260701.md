# WVZ4 新 LOD 机制详解

本文给后续对话或维护者接手用，重点说明当前 WVZ4 新 LOD 的设计目标、写入算法、文件组织、读取和 viewer 渲染策略，以及已经跑过的正确性和性能/体积验证。

## 1. 背景和目标

WVZ4 原始波形数据可以非常大。典型场景是：

- 仿真 cycle 很长，百万到千万级业务 cycle。
- signal 很多，十万到百万级信号定义。
- 某些信号每 cycle 都变化，另一些信号长期稳定或稀疏变化。
- viewer 在全局缩小时不需要每个原始变化点，但在放大后必须能恢复正确波形。

新 LOD 的目标不是简单额外保存一份抽样表，而是：

- 降低大时间窗浏览时的读取和绘制压力。
- 尽量不让 LOD 体积超过原始变化流。
- 让每个原始事件只属于一个层级，避免 raw + LOD 重复保存同一数据。
- 对长时间稳定区，保留最后一次变化，避免后续值显示错误。
- viewer 可以按当前像素时间跨度选择合适 LOD，并在有效区间不足时 fallback。

当前默认写入配置里，LOD 和 residual LOD 都是开启的：

- `WriterOptions::enable_lod_tables = true`
- `WriterOptions::enable_residual_lod_tables = true`
- `WriterOptions::target_block_span = 100000`
- `WriterOptions::signals_per_chunk = 32`

相关代码入口：

- 写入端：`wvz4_writer_typed.h`
- viewer 解析：`QtViewer/WaveParser4.cpp`
- viewer 类型：`QtViewer/WaveTypes.h`
- viewer 绘制：`QtViewer/WaveCanvas.cpp`
- viewer 压测和像素对比 CLI：`QtViewer/main.cpp`

## 2. 核心概念

### 2.1 storage id，而不是 signal id

LOD 按物理 `storage_id` 组织，不按逻辑 signal id 组织。

这样做是为了支持 bitfield、union、alias 等情况。多个逻辑信号可以指向同一段物理存储，只在 `SIGT` 中用 `storage_id + bitOffset + bitWidth` 描述逻辑范围。LOD 只保存 storage 的变化流，viewer 再按 signal 的 bit 范围切出对应显示值。

这可以避免同一底层数据被多个逻辑信号重复追踪、重复压缩、重复 LOD。

### 2.2 raw 在 residual LOD 文件中不是完整真值

新 LOD 是互斥存储。

在开启 residual LOD 的文件里，一个变化事件只会落到以下位置之一：

- residual raw 变化流。
- 某一级 LOD 变化流。

因此，单独看 residual raw 不是完整真值。完整真值需要 parser 把 residual raw 和所有 LOD 事件合并后得到。

这也是为什么视觉一致性验证不能用“同一个 LOD 文件清掉 LOD 再比对”。正确做法是：

- 一份 NoLOD 文件：保存完整 raw 真值。
- 一份 LOD 文件：保存 residual raw + LOD。
- 用 viewer 双文件渲染对比入口比较两者的像素输出。

当前新增入口：

```text
QtViewer.exe --lod-visual-compare-files <raw_no_lod.wvz4> <lod.wvz4> <out_dir> [signals] [steps] [width] [height] [maxDecodedSamples]
```

### 2.3 LOD 层级和 bucket

Residual LOD 当前固定 7 级，bucket 以 10 倍递增：

| level | bucketCycles |
|---:|---:|
| 0 | 10 |
| 1 | 100 |
| 2 | 1,000 |
| 3 | 10,000 |
| 4 | 100,000 |
| 5 | 1,000,000 |
| 6 | 10,000,000 |

这些 cycle 是 writer 内部时间单位。当前压测里 `writer_ticks_per_business_cycle = 10`，所以 1 个业务 cycle 对应 10 个 writer tick。

相关常量在 `wvz4_writer_typed.h`：

```cpp
kLodResidualBaseBucketCycles = 10
kLodResidualLevelMultiplier = 10
kLodLevelCount = 7
kLodMaxRecordsToSourceRatio = 5
```

`kLodMaxRecordsToSourceRatio = 5` 的含义是传统 LOD 路径里每一级最多保留来源记录数的 20%。Residual LOD 路径更进一步使用互斥存储，不再把同一事件同时保存在 raw 和多级 LOD 中。

## 3. 写入端算法

### 3.1 事件先进入 pending

每个 `storage_id` 有一个 `LodStorageState`，里面有：

- `raw_transition_count`
- `has_residual_pending`
- `residual_pending_transition`
- `residual_pending_base_window_start/end`
- `residual_pending_coarsest_window_end`
- `levels[]`

每来一个新变化事件，不会立刻决定前一个事件应该写 raw 还是写 LOD。写入端先保留一个 pending 事件。等下一个事件来了，才能知道 pending 事件是不是某个 bucket 内的最后一次变化。

入口是：

```cpp
update_lod_tables(storage_id, transition)
```

如果 residual LOD 开启：

1. 如果已有 pending，则用当前新事件作为 `next_transition`，决定旧 pending 的归属。
2. 当前新事件成为新的 pending。

### 3.2 为什么使用“bucket 内最后一次事件”

显示波形时，一个 window 内的第一个事件只能影响这个 window 内局部；但最后一次事件会决定后面一大段时间的值。

因此 LOD 代表一个 bucket 时，必须保存 bucket 内最后一次变化，而不是第一次变化。否则会出现这种错误：

```text
前半段很密，后半段没有变化
如果没有保存密集段最后一次变化，后半段稳定值可能整段错误
```

新算法通过 pending 机制天然得到“最后一次事件”：

- 当前事件来了，说明前一个 pending 已经不是“未来未知”。
- 如果当前事件跨出了某一级 bucket，前一个 pending 就是该 bucket 的最后一次事件。
- 写入端把它放到能表达这个事实的最粗 LOD 层。

### 3.3 事件归属规则

函数：

```cpp
place_residual_lod_transition(storage_id, storage, transition, next_transition)
```

规则简述：

1. 如果没有 LOD levels，写 residual raw。
2. 如果没有 `next_transition`，说明这是文件尾部最后 pending 事件，放到可用的最粗 LOD 层，以保证长尾稳定值可见。
3. 如果下一个变化仍在 base bucket 内，说明当前事件太密，写 residual raw。
4. 否则从细到粗检查 bucket，选择“下一个变化已经跨出该 bucket”的最粗层级。
5. 如果没有合适 LOD 层，写 residual raw。

这使得一个事件只出现一次：

```text
raw residual OR LOD level 0 OR LOD level 1 ... OR LOD level 6
```

### 3.4 valid range

LOD 不是全时间范围都有效。某一级只在它实际保存了代表事件的 bucket 范围内有效。

写入端维护每级的 `valid_ranges`：

- 有事件成功进入某级 LOD，就扩展该级有效范围。
- 如果传统 LOD 20% 约束不满足，会关闭当前有效范围。
- Residual LOD 中，有效范围用于告诉 viewer：这一段可以用该级 LOD；不覆盖的区间必须找其它层或 raw。

相关函数：

```cpp
extend_lod_valid_range()
close_lod_valid_range()
materialize_lod_level_valid_ranges()
```

### 3.5 时间块组织

LOD section 使用 `LODZ`，并在 footer 里建立索引。

每一级 LOD 的时间块大小：

```text
lod_time_chunk_span = bucketCycles * target_block_span
```

默认 `target_block_span = 100000`，所以：

| level | bucketCycles | LODZ time chunk span |
|---:|---:|---:|
| 0 | 10 | 1,000,000 |
| 1 | 100 | 10,000,000 |
| 2 | 1,000 | 100,000,000 |
| 3 | 10,000 | 1,000,000,000 |
| 4 | 100,000 | 10,000,000,000 |
| 5 | 1,000,000 | 100,000,000,000 |
| 6 | 10,000,000 | 1,000,000,000,000 |

这样不是“每级都按固定小块切”，而是越粗的 LOD 时间块越大，避免读取时 chunk 数随层级暴涨。

每个 LODZ chunk 还按 signal chunk 组织。当前 `signals_per_chunk = 32`，也就是同一时间块内每 32 个 storage/signal 打一组，避免 10GB 级文件打开时一次拉太多信号。

### 3.6 LODZ 内容

每个 LODZ section 大致包含：

- chunk id
- level index
- signal chunk id
- start cycle / end cycle
- compression type
- raw payload size
- encoded payload size
- encoded payload

payload 内部按 storage 记录：

- storage id
- byte width
- valid ranges
- record count
- record payload

Residual LOD 的 record payload 使用 value residual fast 编码：

```cpp
append_value_residual_fast_record(...)
```

这比普通完整 value 记录更适合互斥 LOD 事件流。

## 4. 读取端算法

### 4.1 footer 先建索引

parser 会解析：

- raw block index
- LOD bucket cycles
- LODZ chunk index
- 每个 LODZ chunk 的 offset/size/range/level/signal chunk

这样 viewer 不需要顺序扫描整个文件，可以按信号集合和时间范围加载。

相关函数：

```cpp
parseFooterSection(...)
decodeLodzChunksFromFooterIndex(...)
```

### 4.2 residual raw 真值重建

如果文件带 residual LOD feature，并且本次 load 要加载 raw samples：

1. 先按 footer index 解 raw WDAT。
2. 再解相关 LODZ。
3. 把 LOD 事件追加回 raw samples。
4. 排序并 compact，形成完整真值 samples。

关键代码：

```cpp
appendResidualLodToRawSamples(...)
```

所以数据正确性测试比较的是 parser 输出后的完整 samples，而不是文件里的 residual raw 原始片段。

### 4.3 LOD 层累计化

Residual LOD 的每个事件只存在一个层级。为了让 viewer 选择某个较细层时也能拿到更粗层保存的长跨度尾锚点，parser 会把更粗层事件向更细层累计。

关键函数：

```cpp
makeResidualLodLevelsCumulative(...)
```

它从粗到细合并：

- `samples`
- `validRanges`
- `loadedRanges`

这样 viewer 拿到 level 2 时，里面已经包含 level 3/4/5/6 中对该 storage 有用的事件。

### 4.4 bitfield 切片

LOD 按 storage 保存，但 viewer 按逻辑 signal 展示。因此 parser 在输出 `WaveSignal` 时会执行：

```cpp
sliceLodLevelForSignal(level, signal)
```

它按 `bitOffset + bitWidth` 从 storage value 中取对应范围，保证 bitfield 不需要在写入端重复保存。

## 5. Viewer 选择和绘制

### 5.1 何时选 LOD

Viewer 计算当前视窗：

```text
cyclesPerPixel = viewSpan / plotWidth
```

当 `cyclesPerPixel < 128` 或信号没有 LOD 时，直接 raw 绘制。

否则选择：

```text
bucketCycles <= cyclesPerPixel 的最粗 LOD
```

代码：

```cpp
chooseLodLevelForViewport(...)
```

这条规则保证 LOD bucket 不会大于一个像素对应的时间跨度，从视觉上不会跳过一个可分辨像素内以外的事件。

### 5.2 valid range fallback

选中某级 LOD 后，viewer 还要检查该级 `validRanges`。

如果当前视窗某段不在 valid range 内：

1. 先尝试其它可用 LOD 层。
2. 最后才用 raw last resort。

关键代码：

```cpp
effectiveLodValidRanges(...)
drawFallbackLodRange(...)
drawRawLastResortRange(...)
```

注意：Residual LOD 文件加载 raw samples 时，parser 已经把 residual LOD 事件补回 raw samples。因此 raw last resort 在正常加载路径下仍然可以得到完整真值。

### 5.3 bit 和 bus 的绘制差异

bit 信号的粗 LOD 样本语义是“该 bucket 有活动”。因此 bit 的 LOD sample 路径仍使用 dense activity block，避免密集 bit 被画丢。

bus 信号在中等密度下如果也按 activity block 填充，会出现视觉上被错误填成一整段绿块的问题。因此当前修复是：

- bus LOD sample 数量不超过像素列数时，按原生 bus frame 画边框。
- bus LOD sample 数量超过像素列数时，才按 dense activity mini-rect 合并。

相关改动在：

```cpp
QtViewer/WaveCanvas.cpp
```

关键变量：

```cpp
lodVisibleCount
lodDenseByPixel
```

### 5.4 双文件像素验证入口

新增 viewer CLI：

```text
--lod-visual-compare-files
```

作用：

- 左侧加载 NoLOD 文件，使用完整 raw。
- 右侧加载 LOD 文件，使用 viewer 正常 LOD 选择路径。
- 两边按相同 signal 名、相同缩放步骤、相同画布尺寸渲染。
- 输出 raw 图、lod 图、diff 图和 CSV。

输出指标包括：

- exact diff pixels
- exact diff ratio
- active raw pixels
- active lod pixels
- active union
- active jaccard
- active miss ratio
- active extra ratio

其中 active pixel 指绿色波形像素。LOD 视觉正确性的核心指标是：

```text
active_jaccard = 1
active_miss_ratio = 0
active_extra_ratio = 0
```

当前测试同时达到了 `exact_diff_ratio = 0`。

## 7. 之前发现并修复的问题

### 7.1 单文件视觉对比不适合 residual LOD

旧入口：

```text
--lod-visual-compare
```

它在同一个 LOD 文件里复制一份 wave，然后清空 `lodLevels` 作为 raw 对照。

这对旧式“raw 完整 + LOD 额外表”的文件可以用，但对 residual LOD 不严格，因为 residual raw 本来就不是完整真值。

修复：

```text
--lod-visual-compare-files
```

用 NoLOD 文件和 LOD 文件两份真实文件比较。

### 7.2 bus 中密 LOD 被错误填绿块

问题现象：

- 某些 bus 在缩小到中等视野时，LOD path 把一段可分辨的稀疏/中密变化画成实心绿块。
- Pixel compare 表现为 `active_extra_ratio > 0`。

原因：

- LOD sample path 对 bus 过早使用 activity fill。
- raw path 在相同视觉尺度下仍然画 bus frame。

修复：

- bus LOD sample 数量不超过像素列数时，画原生 bus frame。
- 超过像素列数才画 dense activity mini-rect。

修复后 dense/sparse 双文件像素对比均为完全一致。

### 7.3 bit 路径不能简单改成线段

尝试过按样本数量把 bit LOD sample path 也切到线段画法，结果 dense case 出现 `active_miss_ratio > 0`。

原因：

- bit 粗 LOD 样本代表 bucket 活动，尤其在全局视野中需要画成 activity block。
- 如果按普通稳定线段画，会丢失密集活动的实心视觉表达。

最终策略：

- bit 维持 LOD activity block。
- bus 做中密线框分流。

## 9. 维护注意事项

1. 不要把 residual raw 当完整真值。
2. 新的 visual compare 要使用两份文件：NoLOD vs LOD。
3. 如果改 LOD 选择规则，必须复跑逐像素验证。
4. 如果改 bitfield/storage id 逻辑，必须复跑 raw compare，因为 LOD 是按 storage id 保存再切片。
5. 如果改 `target_block_span` 或 `signals_per_chunk`，需要重新评估 10GB 级文件的 load 时间和 LODZ chunk 数量。
6. 如果改 bucket 层级，viewer 的 `chooseLodLevelForViewport` 仍要保证 `bucketCycles <= cyclesPerPixel`。
7. 如果视觉上出现前导块、绿块、黑缝，先跑 `--lod-visual-compare-files`，不要只凭截图猜。

## 10. 当前结论

当前新 LOD 已经满足：

- 数据正确性：NoLOD 和 LOD parser 输出逐样本一致。
- 文件体积：大规模 case LOD 文件明显小于 NoLOD。
- 视觉正确性：dense 和 sparse case 开关 LOD 双文件逐像素一致。
- 10GB 级适配方向：LODZ 按时间块和 32 signal chunk 组织，支持后续按需加载，不需要一次读完整文件。
